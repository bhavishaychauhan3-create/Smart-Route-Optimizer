Foundational Theory

What is Dijkstra's Algorithm?

Uniform-cost shortest path search on non-negative weighted graphs using Min-Heap priority queues.

Dijkstra's Algorithm (Uniform-Cost Search)

Radial 360° Wavefront Expansion • Zero Heuristic • Guaranteed Optimal
  • Core Mechanism: Traverses graphs radially in 360°, finalizing nodes strictly by ascending accumulated cost $g(n)$.
  • Data Structure: Binary Min-Priority Queue (heapq in Python) with $O((V+E)\log V)$ runtime.
  • Edge Relaxation: Dynamically updates shortest distance if a cheaper path through vertex $u$ is found.
  • Trade-Off: Blind exploration—searches backwards and sideways away from target, consuming extra RAM on road maps.
d(v) = min [ d(v), d(u) + w(u, v) ]   (Edge Relaxation Condition)

Step-by-Step Execution Process:

  • 1
    Initialization: Set distance $d(\text{start}) = 0$ and $d(v) = \infty$ for all other vertices. Push $(\text{cost}=0, \text{start})$ into a Min-Priority Queue.
  • 2
    Extract Minimum: Pop the vertex $u$ with the smallest tentative distance from the priority queue.
  • 3
    Edge Relaxation: For each neighbor $v$ of $u$ connected with edge weight $w(u, v)$: if $d(u) + w(u, v) < d(v)$, update $d(v) = d(u) + w(u, v)$, record predecessor pointer $P[v] = u$, and push $v$ into the queue.
  • 4
    Termination & Backtracking: Once the target node is extracted from the queue, stop and backtrack from target to start via predecessor pointers.
Advantages
  • Guaranteed mathematically optimal path
  • Finds shortest path to all destinations simultaneously
  • Requires zero spatial coordinates or heuristic knowledge
  • Versatile across any non-negative weighted graph
Disadvantages
  • Blind radial exploration: wastes memory exploring in reverse directions
  • High latency on large continental road maps
  • Cannot handle negative edge weight cycles
  • Memory footprint grows quadratically with graph radius

Heuristic Search

What is A* (A-Star) Algorithm?

Goal-directed shortest path algorithm combining accumulated cost $g(n)$ with admissible Haversine heuristic $h(n)$.

A* Search Algorithm (Heuristic-Directed)

Goal-Directed Elliptical Cone • Admissible Haversine Heuristic • Up to 80% Fewer Nodes
  • Core Function: Evaluates nodes using $f(n) = g(n) + h(n)$ to steer the priority queue toward the target.
  • Heuristic Selection: Uses great-circle Haversine distance, guaranteeing mathematical admissibility ($h(n) \le h^*(n)$).
  • Search Geometry: Prunes up to 74% of road network nodes by bounding exploration inside a directed elliptical cone.
  • Data Structure: Min-Heap prioritizing lowest $f(n)$ score with tiebreaker counters.
f(n) = g(n) + h(n)
g(n): Exact cost from start to node $n$ h(n): Estimated cost from node $n$ to goal f(n): Total estimated route cost through $n$
Crucial Concept: Admissibility & Consistency

For A* to guarantee the true shortest path, the heuristic $h(n)$ must be admissible: it must never overestimate the true cost to reach the goal ($h(n) \le h^*(n)$). In navigation networks, the straight-line Haversine Great-Circle distance is universally admissible because the shortest distance between two points on Earth is the spherical chord; no drivable road can ever be shorter than straight-line distance!

Step-by-Step Execution Process:

  • 1
    Open & Closed Sets: Maintain an Open Set (priority queue of frontier candidates sorted by $f(n)$) and a Closed Set (already evaluated nodes).
  • 2
    Goal Directed Extraction: Pop the node $u$ with the lowest $f(u) = g(u) + h(u)$.
  • 3
    Target Validation: If $u == \text{target}$, the optimal shortest path has been found. Terminate immediately.
  • 4
    Neighbor Evaluation: For each neighbor $v \notin \text{Closed Set}$, calculate tentative $g = g(u) + \text{weight}(u, v)$. If tentative $g < g(v)$, update $g(v)$, calculate $f(v) = g(v) + \text{Haversine}(v, \text{target})$, record predecessor, and add to Open Set.
Advantages
  • Dramatically fewer nodes explored (saves 40%–80% compute)
  • Massively faster query latency for point-to-point GPS
  • Guaranteed optimal shortest path with admissible heuristic
  • Standard engine behind Google Maps, Tesla, and OSRM
Disadvantages
  • Requires geographic coordinates (lat/lon) to calculate heuristic
  • Higher calculation overhead per individual node ($g+h$)
  • Inadmissible heuristic will return suboptimal paths
  • Only evaluates routes to one designated target at a time

Core Modules in graph_engine.py & app.py

1. Graph Representation

Represented as an adjacency list dictionary adj: Dict[str, List[Tuple[str, float, dict]]] where vertices represent physical road intersections with GPS coordinates (lat, lon). Edge weights represent true drivable road distance in kilometers.

2. Haversine Distance Calculation

Calculates great-circle distance between two points on a spherical Earth of radius $R = 6371.0\text{ km}$:

a = sin²(Δφ/2) + cos(φ₁)cos(φ₂)sin²(Δλ/2)
d = 2R · atan2(√a, √(1−a))

3. Dijkstra Implementation

Utilizes Python's standard heapq min-priority queue storing tuples (current_distance, node_id). Guarantees logarithmic $O(\log V)$ node insertions and pop operations.

4. A* Implementation

Stores (f_score, node_id) in the priority queue, where $f = g + h$. Tracks g_score dictionary for exact path cost, ensuring no re-exploration of settled nodes when the heuristic is monotonic.

5. Multi-Stop TSP 2-Opt Optimization

Solves the Traveling Salesperson Problem across intermediate waypoints using iterative 2-opt edge-swap heuristics to minimize detour mileage.

Mathematical Rigor

Computational Complexity Analysis

Asymptotic time and space requirements analyzed over road network topologies.

Dijkstra's Complexity

Time Complexity:
  • Binary Min-Heap: O((V + E) log V)
  • Fibonacci Heap: O(E + V log V)
  • Unsorted Array: O(V²)
Space Complexity:

O(V) required to store the distance array, predecessor dictionary, and priority queue states.

Why it scales poorly for GPS: For nationwide maps ($V > 10^7$ nodes), exploring in all radial directions exhausts RAM and introduces high latency.

A* Search Complexity

Time Complexity:
  • Best Case (Perfect heuristic): O(d) linear along the path
  • Typical Road Graph: O(α · (V + E) log V) where α ≪ 1
  • Worst Case (Deceptive heuristic): O(b^d) exponential
Space Complexity:

O(V) to retain the Open Set priority queue and Closed Set hash table in memory.

Why GPS systems rely on A*: With the Haversine distance heuristic, the practical search space is bounded inside an ellipse, keeping $V_{\text{explored}}$ tiny.

Summary & Insights

Conclusion: When to Use Which?

Architectural guidelines for selecting the optimal routing algorithm in production engineering.

When to Select Dijkstra

  • Unknown Destination: Finding the closest hospital, EV charger, or gas station among multiple candidates.
  • Single-Source All-Destinations: Precomputing routing tables in network switches (OSPF, IS-IS).
  • Non-Spatial Graphs: Dependency trees, state machines, and abstract graphs lacking physical coordinates.

When to Select A* Search

  • Point-to-Point GPS Navigation: Fast, turn-by-turn route calculations between known coordinates (e.g. Mullana → Ambala).
  • Robotics & Autonomous Driving: Dynamic trajectory planning and obstacle evasion in real time.
  • Video Games: AI pathfinding over 2D/3D navigation meshes where memory is constrained.

Key Takeaway: A* is strictly an optimization of Dijkstra that leverages the Haversine heuristic to prune up to 80% of unnecessary node evaluations. When $h(n) = 0$, A* collapses back into standard Dijkstra.
